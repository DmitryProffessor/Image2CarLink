## Обзор

Проект включает офлайн-конвейер оценки и готовый к запуску сервис поиска автомобилей. Получив полное изображение и заданную вызывающей стороной ограничивающую рамку автомобиля (BBox), сервис вычисляет вектор визуальных признаков, ищет похожие объекты в галерее и возвращает аннотации с наивысшими оценками. Если заданный порог принятия не достигнут, возвращается пустой список кандидатов.

Автоматическое распознавание номерных знаков (ALPR) может давать сбои, если знаки загрязнены, перекрыты, пострадали от погоды или бликов либо находятся вне поля зрения камеры. Вместо этого проект использует визуальное сходство для повторной идентификации автомобилей. Сервис не выполняет ALPR, распознавание лиц, обнаружение объектов или трекинг и не использует метаданные камеры, времени или местоположения. Изображения должны соответствовать протоколу анонимизации набора данных: номера и лица должны быть размыты. Перед извлечением признаков маскируется фиксированная нижняя центральная область фрагмента; это эвристика, которая не гарантирует исключения пикселей номера за пределами маски. Универсальный визуальный дескриптор не выделяет лица отдельно, однако размытые пиксели лица в оставшейся части фрагмента могут влиять на общие цветовые и пространственные характеристики. Для строгого исключения на уровне пикселей необходимы предоставленные маски приватности либо утверждённая политика маскирования/обнаружения.

**Входит в область проекта:** обрезка изображения по BBox, построение эмбеддингов, поиск по галерее, ранжирование и отклонение результатов.

**Не входит в область проекта:** обнаружение автомобилей, ALPR и трекинг. Координаты BBox должен передавать вызывающий сервис.

Текущий дескриптор — детерминированная базовая реализация на вручную заданных признаках, а не обученная нейросетевая модель повторной идентификации. Заявлений о точности обученной модели или калибровке порога нет.

## Возможности

- Сервер инференса на FastAPI с автоматически создаваемой схемой OpenAPI и Swagger UI
- Веб-клиент для добавления примеров в галерею и поиска совпадений
- PostgreSQL 15 и pgvector для поиска по косинусному расстоянию
- Проверка изображений и BBox с возвратом HTTP-ошибок
- L2-нормализованные эмбеддинги размерности 386 типа `float32`
- Настраиваемые top-N и порог отклонения
- Загрузка галереи из CSV и каталога изображений либо через API
- Офлайн-генерация `embeddings.npy`, `submission.csv` и `candidates.csv`
- Инструменты оценки mAP, Rank-1/Rank-5 и метрик предложения кандидатов
- Среда для локального запуска через Docker Compose

## Архитектура и конвейер

```text
Браузер (веб-сервис :8080)
        |
        | multipart-запрос формы
        v
Сервис инференса FastAPI (:8000)
  1. Приём: декодирование JPEG/PNG и проверка BBox по размеру кадра
  2. Обработка: обрезка, маскирование нижней центральной области, построение нормализованного 386-мерного вектора
  3. Поиск: запрос к PostgreSQL/pgvector по косинусному расстоянию
  4. Результат: возврат принятых top-N совпадений или пустого списка
        |
        v
```

Браузерный клиент вызывает API непосредственно из браузера пользователя. В галерее хранятся визуальные векторы, идентификаторы исходных изображений, BBox и время добавления `created_at`. Метаданные камеры, времени и местоположения съёмки, а также `vehicle_id` не сохраняются и не используются для поиска.

## Требования и запуск

### Docker Compose (рекомендуется)

Необходимы Docker Engine/Desktop и плагин Compose. Выполните команды из корневого каталога репозитория:

```powershell
Copy-Item .env.example .env
docker compose up --build -d
docker compose ps
```

В macOS/Linux вместо первой команды используйте `cp .env.example .env`. Compose также запускается со встроенными значениями по умолчанию без файла `.env`. Сервисы будут доступны по адресам:

| Сервис | Локальный адрес / порт | Назначение |
|---|---|---|
| `web` | http://localhost:8080 | Браузерный клиент (nginx без привилегий) |
| `api` | http://localhost:8000 | API инференса |
| Документация `api` | http://localhost:8000/docs | Swagger UI |
| OpenAPI `api` | http://localhost:8000/openapi.json | JSON-схема OpenAPI |
| `db` | `localhost:5432` | PostgreSQL + pgvector |

Docker Compose запускает сначала базу данных, затем API и веб-клиент. Для всех сервисов настроены проверки состояния. Чтобы остановить проект:

```powershell
docker compose down
```

Чтобы также удалить постоянный том базы данных (вместе с проиндексированными векторами галереи), выполните:

```powershell
docker compose down -v
```

### Локальная разработка API

В образе сервиса используется Python 3.12. Создайте виртуальное окружение и установите зависимости зафиксированных версий:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r backend\requirements.txt
```

Для локального запуска API необходим работающий PostgreSQL с расширением pgvector и корректно настроенный `DATABASE_URL`. Запустите API командой:

```powershell
python -m uvicorn backend.app.main:app --host 0.0.0.0 --port 8000
```

### Офлайн-генерация файлов

Для офлайн-конвейера используются NumPy и OpenCV:

```powershell
python -m pip install -r requirements-data.txt
python reid_pipeline.py --dataset .\dataset --output .\artifacts --confidence-threshold 0.65
```

Эта команда устанавливает зависимости для генерации файлов и оценки. Для запуска необходим набор данных описанной ниже структуры. Три файла для участия в задании будут сохранены в каталоге `artifacts/`.

Чтобы инициализировать галерею в Compose, подготовьте файлы в следующей структуре:

```text
dataset/
├── images/
│   ├── <image_id>.jpg
│   └── ...
└── test_gallery.csv
```

Для импорта галереи при запуске CSV должен содержать столбцы `image_id,x,y,w,h`. Если CSV или каталог изображений отсутствует, API запускается с пустой галереей, которую можно наполнить через браузер или API. Перед записью все строки CSV проверяются и преобразуются в эмбеддинги, после чего добавляются в одной транзакции базы данных. При ошибках импорта нормальный запуск прерывается: некорректные строки не пропускаются молча.

Повторный импорт обновляет записи с неизменившимися идентификаторами аннотаций, но не удаляет элементы, отсутствующие в новой версии CSV. Чтобы полностью заменить галерею, остановите сервисы и удалите постоянный том базы данных командой `docker compose down -v`, а затем запустите проект с новыми данными. Старые векторы из таблицы `vehicle_gallery` не мигрируются: прежняя схема не сохраняла BBox и поэтому не могла различать несколько аннотаций автомобилей в одном кадре.

## Набор данных и входные изображения

Офлайн-набор данных для задания имеет следующую структуру:

```text
dataset/
├── images/                  # Каталог кадров JPEG/PNG без вложенных подкаталогов
├── train.csv                # image_id,x,y,w,h,vehicle_id
├── test_query.csv           # image_id,x,y,w,h
└── test_gallery.csv         # image_id,x,y,w,h
```

`x` и `y` — координаты верхнего левого угла, а `w` и `h` — положительные ширина и высота в пикселях исходного кадра. Каждая строка описывает одну аннотацию автомобиля; у нескольких аннотаций может совпадать `image_id`. API определяет ширину и высоту кадра по декодированному изображению. Каждый BBox должен полностью помещаться в его реальные границы. API принимает JPEG и PNG. При импорте галереи поиск изображения выполняется либо по точному имени файла в `images/`, либо по `image_id` с расширением `.jpg`, `.jpeg` или `.png`. Помимо ограничения размера загружаемого файла, настраиваемые лимиты по умолчанию отклоняют изображения шириной более 8192 пикселей, высотой более 8192 пикселей или размером свыше 20 000 000 пикселей.

По протоколу задания множества `vehicle_id` в обучающей и тестовой выборках не пересекаются. Инференс не читает `train.csv` и не использует обучающие метки; значения `vehicle_id` и `camera_id` не передаются в сервис галереи и не используются им. Сервис ищет среди аннотаций, добавленных через API или импортированных из `test_gallery.csv`. Идентификатор записи галереи детерминированно вычисляется с помощью SHA-256 по исходному `image_id` и координатам BBox, поэтому несколько рамок в одном кадре считаются разными записями. Идентификаторы исходных изображений и BBox хранятся для отслеживания аннотаций, но не используются как признаки сходства.

## API

Для передачи изображений во всех конечных точках используется `multipart/form-data`. Для изображений необходимо указать тип содержимого `image/jpeg` или `image/png`. Swagger UI доступен по адресу `/docs`.

| Метод и путь | Назначение | Успешный ответ |
|---|---|---|
| `GET /health` | Проверка доступности API и базы данных | `200 {"status":"ok"}` |
| `GET /api/v1/gallery` | Получение количества элементов в индексе галереи | `200 {"items": <count>}` |
| `POST /api/v1/gallery/items` | Добавление или замена эмбеддинга аннотации в галерее | `201`, идентификатор аннотации, исходного изображения и статус |
| `POST /api/v1/retrieve` | Ранжирование кандидатов галереи для фрагмента запроса | `200`, кандидаты или отказ |

### Добавление элемента в галерею

Поля multipart-запроса: `image_id`, `image` (JPEG/PNG), `x`, `y`, `w` и `h`.

Пример запроса:

```powershell
curl.exe -X POST http://localhost:8000/api/v1/gallery/items `
  -F "image_id=gallery-001" `
  -F "x=20" -F "y=30" -F "w=300" -F "h=180" `
  -F "image=@.\vehicle.jpg;type=image/jpeg"
```

Пример ответа:

```json
{
  "gallery_id": "a deterministic annotation hash",
  "image_id": "gallery-001",
  "status": "stored"
}
```

`image_id` идентифицирует исходный кадр; сервис вычисляет стабильный `gallery_id` аннотации на основе этого идентификатора и BBox. Поэтому разные BBox в одном кадре хранятся в галерее отдельно. Повторный запрос с тем же идентификатором кадра и BBox обновляет вектор существующей аннотации.

### Поиск кандидатов

Поля multipart-запроса: `image` (JPEG/PNG), `x`, `y`, `w`, `h`, необязательные `query_id` и `top_n`.

```powershell
curl.exe -X POST http://localhost:8000/api/v1/retrieve `
  -F "query_id=query-001" `
  -F "x=20" -F "y=30" -F "w=300" -F "h=180" `
  -F "top_n=10" `
  -F "image=@.\query.jpg;type=image/jpeg"
```

Ответ с совпадением:

```json
{
  "query_id": "query-001",
  "candidates": [
    {
      "gallery_id": "gallery-001",
      "score": 0.82,
      "confidence": 0.91
    }
  ],
  "rejected": false,
  "threshold": 0.65,
  "metric": "cosine"
}
```

Ответ при отклонении запроса:

```json
{
  "query_id": "query-001",
  "candidates": [],
  "rejected": true,
  "threshold": 0.65,
  "metric": "cosine"
}
```

`score` — косинусное сходство. Значение `confidence = (score + 1) / 2` — монотонное преобразование оценки, **а не откалиброванная вероятность**. Запрос отклоняется, если ни один кандидат в найденной выборке top-N не достигает `REJECTION_THRESHOLD`. Значение по умолчанию `0.65` перенесено из офлайн-базовой версии и не выбрано на основе результатов валидации. Для практического или хакатонного использования порог следует откалибровать на размеченной валидационной выборке и привести значения F1/TNR/PR-AUC.

### Ошибки HTTP

| Код | Значение |
|---:|---|
| `400` | Некорректные или пустые данные изображения, неверный BBox либо BBox выходит за границы декодированного кадра |
| `413` | Размер загрузки превышает `MAX_IMAGE_BYTES` |
| `415` | Неподдерживаемый тип содержимого изображения |
| `422` | Отсутствуют или некорректно заданы поля multipart-запроса |
| `503` | База данных или хранилище поиска недоступны |

## Браузерный клиент

После запуска `docker compose up --build -d` откройте http://localhost:8080. На странице доступны формы для добавления изображений в галерею и отправки запроса с изображением и BBox. Результат отображается в формате JSON; при отклонении запроса список кандидатов будет пустым. По умолчанию страница обращается к API по адресу `http://localhost:8000`. Если публичные адреса сервисов отличаются, измените `apiBase` в [web/index.html](web/index.html). Multipart-запросы читаются асинхронно; декодирование изображений, извлечение признаков и обращения к базе выполняются в пуле рабочих потоков. Для соединений с базой используется ограниченный пул psycopg.

## Эмбеддинги и оценка сходства

В онлайн- и офлайн-конвейерах используется один и тот же детерминированный дескриптор:

1. Вырезать фрагмент изображения по переданному BBox.
2. Замаскировать нижнюю центральную полосу фрагмента (начинается на уровне 58% высоты; занимает область от 18% до 82% ширины).
3. Изменить размер до `128x128`.
4. Объединить 96 значений HSV-гистограммы, 288 значений среднего и стандартного отклонения каналов в пространственных областях и 2 статистики границ Собеля.
5. L2-нормализовать вектор `float32` из 386 значений.

PostgreSQL хранит векторы типа `VECTOR(386)` в таблице `vehicle_gallery_items`. Ключом служит идентификатор каждой аннотации; исходный ID изображения и BBox сохраняются для отслеживания. При поиске записи сортируются по косинусному расстоянию pgvector (`<=>`), а сходство вычисляется как `1 - cosine_distance`. Векторы галереи нормализуются перед вставкой и поиском. При одинаковых оценках для детерминированного ранжирования используется `gallery_id`. Эта базовая версия опирается на статистику цвета, пространственного расположения и границ; она не является обученной моделью внешнего вида и может ненадёжно различать автомобили с похожим обликом или значительными отличиями ракурса и освещения.


Генератор создаёт:

- `submission.csv`: для каждого запроса — до 10 ID галереи, отсортированных по убыванию косинусного сходства
- `embeddings.npy`: сначала эмбеддинги запросов, затем эмбеддинги галереи, в порядке строк исходных CSV
- `candidates.csv`: принятые пары «запрос — элемент галереи» с оценкой confidence; для запроса без принятых пар строки отсутствуют

Файлы `embeddings.npy`, `submission.csv` и `candidates.csv` в корневом каталоге, если они присутствуют в локальной копии, являются устаревшими и **не соответствуют** размеру CSV в корне или текущему конвейеру с векторами размерности 386. Не отправляйте их как актуальные результаты. Копия репозитория не содержит кадров из `dataset/images/`, поэтому корректно пересоздать эти бинарные файлы здесь нельзя. Перед генерацией файлов для отправки подготовьте полный набор данных, предоставленный организаторами.

Для вычисления метрик используйте файл эталонной разметки от организаторов:

```powershell
python evaluate.py `
  --gt .\test_ground_truth.csv `
  --submission .\artifacts\submission.csv `
  --candidates .\artifacts\candidates.csv `
  --embeddings .\artifacts\embeddings.npy `
  --query .\dataset\test_query.csv `
  --gallery .\dataset\test_gallery.csv `
  --json .\artifacts\report.json
```

Оценщик рассчитывает mAP@10, Rank-1, Rank-5, mAP/mINP по полному ранжированию, а также precision, recall, F1, TNR и PR-AUC для кандидатов, если предоставленная эталонная разметка позволяет их вычислить. Если в выборке нет запросов open-set, метрика TNR недоступна. В этом README не заявлены результаты бенчмарков.

В имеющемся в проекте `train.csv` есть дополнительный столбец `camera_id`; генератору нужны только столбцы аннотаций и `vehicle_id`, метаданные камеры не используются. В [README_data.md](README_data.md) описан протокол задания для `test_query.csv` и `test_gallery.csv`. Универсальный `test.csv` не подходит на замену: в нём нет разделения на запросы и галерею.

## Обучение, зависимости и воспроизводимость

Сервис поиска не использует цикл обучения модели или файл весов нейросети. Дескриптор детерминирован, API не применяет случайную выборку. Версии зависимостей зафиксированы в [backend/requirements.txt](backend/requirements.txt); файл `requirements.txt` включает зависимости сервера и оценщика. Для базовых образов контейнеров указаны версии. Для автономного развёртывания заранее соберите или загрузите образы и сохраните колёса Python-пакетов и исходный код до отключения от сети; скачивать веса модели не требуется.

Исходный детектор `weights/yolov8m.pt` не используется сервисом и намеренно исключён из процесса повторной идентификации. При реализации поиска не используются внешние предварительно обученные веса или сторонние наборы изображений.

## Ограничения

- Дескрипторы на вручную заданных признаках — облегчённая базовая версия; точность поиска между камерами не подтверждена предоставленными результатами тестирования.
- Линейное преобразование оценки не является вероятностной калибровкой. Порог `0.65` необходимо проверить на распределении целевой галереи.
- PostgreSQL хранит идентификаторы аннотаций, исходных изображений, BBox и векторы; API не сохраняет загруженные изображения.
- В браузерном клиенте пользователь должен самостоятельно задать координаты BBox.
- Не настроены аутентификация, авторизация, TLS, ограничение частоты запросов и управление секретами для промышленной среды. Не публикуйте этот демонстрационный стек напрямую в недоверенной сети.
- Файлы набора данных и эталонная разметка организаторов не включены. Для демонстрации положительных совпадений необходимо заполнить галерею.
- Входные изображения должны быть предварительно анонимизированы. Геометрическая маска номера в нижней центральной части покрыта модульным тестом, но она не является детектором номерных знаков и не гарантирует полного исключения влияния пикселей за пределами маски. Пиксели лиц, остающиеся на изображении после размытия, также могут влиять на общую статистику; для строгого исключения пикселей лиц нужны размеченные маски приватности или утверждённая политика.
