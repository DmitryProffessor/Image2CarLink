# The service for generating a digital feature of the TC — a dataset.

## Composition

dataset/
images/ all images, flat catalog, JPEG or PNG
train.csv image_id, x, y, w, h, vehicle_id
test_query.csv image_id, x, y, w, h
test_gallery.csv image_id, x, y, w, h


## Annotation format

Each annotation row describes one vehicle. Multiple rows may reference the same
frame when that frame contains multiple annotated vehicles.

`x, y, w, h` — The coordinates of the bounding rectangle of the TC in pixels of the original frame (top‑left corner, width, height).

`vehicle_id` — An integer identity identifier, present only in `train.csv`. The `vehicle_id` sets in train and test do not overlap.

The inference pipeline uses only the image, BBox and image ID. Extra CSV fields
such as `camera_id`, if present in local training data, are ignored and are not
used to build features or rank results. The challenge query/gallery files used
by the artifact generator are `test_query.csv` and `test_gallery.csv`; a generic
`test.csv` without query/gallery roles is not sufficient to produce the ranked
submission format.

## Problem statement

For each object in `test_query.csv`, it is necessary to sort the objects in `test_gallery.csv` in descending order of the probability of belonging to the same vehicle.

## Anonymization

State registration plates and people’s faces in the frame are blurred.
Using any residual features of the license plate to solve the task is prohibited — solutions based on such features are not allowed for the final assessment.

The dataset specification covers varying lighting and weather, front/side/rear
viewpoints, partial occlusion, and low image quality. The archive images are not
present in this repository checkout, so this coverage has not been independently
verified or evaluated by condition here.

## How to submit the solution

The solutions are checked manually by the organizers after the hackathon ends.
There is no automatic leaderboard during the hackathon.

### Artifacts in the repository

1. **submission.csv** — for each query, the first 10 candidates from the gallery.
   in descending order of proximity:

query_id, gallery_id_1, gallery_id_2, ..., gallery_id_10


2. **embeddings.npy** — vectors of all objects in the test set, order:
   First, all `image_id` from `test_query.csv` (in the order of the file), then all `image_id` from `test_gallery.csv`. The organizers use this file to verify that submission.csv was generated by a real model, not by manual entry.

3. **candidates.csv** — the result of the candidate proposal mode: for each query — a list of accepted candidates with a confidence score, or an empty response (refusal):

query_id, gallery_id, confidence

   The cutoff threshold is selected by the team independently and justified in the solution’s README file.

4. **Code and environment** — the source code for training and inference, `Dockerfile`,  `docker-compose.yml`, and the dependencies file.  The inference is run with a single command in an isolated environment, without internet access (all weights are included in the solution).

## Efficiency

The final measurements are taken by the organizer using standardized equipment after the hackathon, following a standardized script. The participant’s own speed measurements  in the report are for reference only and do not affect the scores.

- Time to generate a feature per TS, batch=1.
- Throughput (FPS) during batch processing, without memory or queue degradation.
- Total weight size — no more than 2 GB.
- Inference should not lead to Out-of-Memory on the test set.

## External resources

The use of public pre-trained weights and open datasets is permitted and encouraged. All sources are listed in the solution’s README.
Solutions based on closed, proprietary, or non-reproducible data are not allowed for evaluation.
